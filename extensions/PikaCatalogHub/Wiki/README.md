# 智能货源中心

本说明对应候选 PikaCatalogHub `0.6.9` / PikaSupplySync `1.1.17`，包含分类图能力及独立受信补图入口。1.1.17 的诊断增强不改变本页分类与入库流程；源码、固定制品、隔离与部署分别以[项目状态](../../../docs/PROJECT_STATUS.md)为准，不以版本号代替真实验收。新用户可先看[操作路径与截图](../../../docs/USER_GUIDE.md)。

## 普通用户只走这一条流程

选择首次分类方式 → 添加货源、设置加价 → 后台分析 → 确认冻结分类及价格 → 后台入库。

### 首次分类方式

- **智能分类（`smart`，默认）**：旧配置和未指定模式的任务仍按原流程创建平台／可选系列／货源层／上游分类，不因升级自动改为镜像。
- **保留上游分类结构（`mirror`，首次入库）**：必须明确选择，且上游使用协议 `0`。以合成路径 `分类甲 → 分类乙 → 分类丙` 为例，下游保留源站实际存在的这三层；后台显示名即使是「演示货源」也不会额外插入树中，不会删除源站原有的中间分类。

分类图能力由配套 Hub 与 Supply 提供；当前候选组合为 `0.6.9`／`1.1.17`。已具备所需目录／图标协议能力的源端，不因接收端诊断版本升级就必须再次升级；实际能力每次严格校验，不另作未经验证的最低版本承诺。已支持 v2 但未声明图标能力的旧源继续原镜像流程；连 v2 都不支持的源仍停止，不猜错误降级或发第二个目录版本请求。需要更新时先源站再接收端，源站须通过既有整包安装流程维护 registry 并启用 PikaCatalogHub；PikaSupplySync 作为依赖须完整安装并能通过 registry 校验，不能只复制新 PHP 文件。源站已有的 `smart` 设置保持不变，提供镜像目录不要求源站改为 `mirror`，也不要求为此启动周期同步或入库任务。接收端仍须明确分析、确认后才入库。

镜像显示完整路径及上游分类 ID，不提供智能一级/二级编辑框；确认按来源＋稳定分类 ID，不合并异父同名或不同来源分类。模式在分析排队时冻结，确认后沿用同一方案；有既存映射的来源不能切换模式。上游没有配套能力、祖先缺失/停用/权限不明、父链跨 owner、循环、重复 ID 或超限均停止，绝不猜父节点或压平。原生分类组（含过滤后的空组）与挂商品分类仍各限 200；完整必要祖先树按 ID 去重独立限 2048，祖先最多 100 层、商品最多 10000 件。本站全体映射 2048 节点／1 MiB、HTTP／快照 16 MiB 等独立门保持，不是每来源额外获得 2048 容量。

这不是持续分类同步：后续上游改名、移动、删除或排序不会自动执行；已建立 ID 的改名/移动在再次分析/入库前拒绝，需另行讨论迁移。新建分类采用本次冻结排序，复用分类保留本站现有排序（含手工排序），纯排序差异不阻断复用。未请求镜像时仍使用原共享目录；v2 采用签名覆盖的 `pika_category_tree=2` 请求，只返回授权商品的 code/category_id/stock 和必要分类的 id/pid/name/sort。商品名真正不传输、不填空、不用于计划；不删除商品或放宽分类校验，不导出内部 owner、用户组配置或商品 config。旧 flag1/schema1 严格契约保留。新商品仍另取详情并执行原名称等校验，预览成功不是全部可入库。请求业务数据只读，但原生 HTTP 日志/WAF 缓存可能写入；不宣称数据库事务时点快照。

分类图与商品封面是独立能力，不能通过重新入库或周期图片同步补齐已有分类图标。本候选准备不执行生产补图、入库或交易；历史隔离证据及未覆盖范围见项目状态。

### 分类图与受信维护入口

合法 v2 响应在外层声明整数 `pika_category_icons:1`；仅完整校验成功后，新计划才冻结 `category_icons:true`。无声明的旧源、无能力位的旧快照仍原样，不迁移旧文件或重算旧 hash。新建缺失节点才额外请求同一路径的签名 `pika_category_tree=3` 和升序唯一 `pika_category_ids`（1–100 项）；响应只有 schema/capability/categories，节点为 id/pid/name/sort/icon，没有商品字段。服务端内部仍先调用原生授权目录，再校验所选分类在授权闭包内，不代表服务端没有读取商品。

图片使用既有 HTTPS/公共 DNS/固定 IP/禁止跳转与代理/MIME/尺寸/缓存安全门，和商品共用原 RunBudget。上游空图或 `/favicon.ico` 保持默认；非法元数据、权限、网络或图片失败会停止，不伪装成缺图。已有分类不因新入库覆盖图标；这不是周期分类图同步。

已有受管镜像的补图只通过已安装的 `local-extensions/extensions/PikaCatalogHub/bin/category-icons.php`。三个模式的完整参数见该 CLI `--help`；实际执行须使用本次已核实站点、来源、ID 和文件 SHA，不复制示例 ID 到生产。

- `preview`：最多 16 个升序唯一 ID，只读精确映射和一次元数据操作，输出到站外私有计划；不下载图片、不写业务行。元数据底层保留既有只读请求有限重试，并非所有网络错误都只发一次。
- `apply`：核验计划 SHA 和来源/映射未漂移，跳过本地手动图及上游默认图；准备全部缓存并先独占保存私有回执，随后全批条件写入 `icon`。失败保留回执/缓存，不自动重试；结果未知先对账。
- `rollback`：核验本批回执 SHA，仅当整批仍处于回执的新值时恢复旧图。手改、混合或身份漂移拒绝，不重建分类、不恢复整库，也不删除共享缓存。

运行用户必须是非 root 的站点 runtime owner；Hub 必须启用，Supply 可停用，不依赖本站 Web、worker 或 timer。计划/回执父目录须在站点外、canonical、运行用户所有且 `0700`，文件须为 `0600` 单链接普通文件；已存在输出不覆盖。维护期间可能创建/写源锁、map 锁和安全图片缓存；不能据此声称文件系统零写。旧 jobs/snapshot/map、商品、层级及加价不应因补图改变，需由运维对账；桌面/手机真实显示另验。

不需要先在异次元「店铺共享」添加。这里直接使用原生 shared 记录；原生「接入货源」会绕过智能分类与后台控制，普通用户不要点击。底层原生入口只供高级维护。

### 1. 添加货源

填写上游提供的 HTTPS 根地址、商户 ID、KEY，另取一个方便辨认的显示名称。公开版本没有预置真实货源或联系方式。

| 协议选项 | 原生值 | 何时选择 |
|---|---:|---|
| 异次元(V3.1.2 重构后全新版) | `0` | 默认，新版异次元 |
| 异次元(V3.1.1 之前旧版) | `2` | 上游明确说明旧版时 |
| 萌次元(V4.0) | `1` | 上游为萌次元时 |

不知道版本时向上游确认，不要按编号大小猜测，也不自动轮流尝试凭据。仅支持 HTTPS/443/公共 DNS；验证证书、固定已验证 IP、禁止重定向与代理。KEY 为 8–64 位，不含空白或控制字符。

点击「测试并接入」，成功连接后保存官方货源，再创建分析任务。若保存成功而任务创建失败，刷新确认列表后对该条「智能分析」，不要重复添加。KEY 不回显，不放入 Pika 状态、快照、日志或草稿，只进入本次请求与官方 shared.app_key；编辑时空 KEY 保留旧值。

### 2. 设置本次加价

首次默认 0%，站长自行决定利润。成本 100、加价 10% 的示意售价是 110；实际币种换算和小数精度依既有价格规则。

分析前可填加价草稿，确认区再次显示本次比例。已有货源可沿用上次已确认比例；明确确认后才用于本次新商品入库。这不是批量调整已有商品售价，既有商品仍按幂等规则处理。

未确认的加价/分类草稿仅保存在当前标签页、当前登录作用域的 sessionStorage 中，受有效期和大小限制；刷新可恢复有效草稿，但不保证退出登录、换浏览器/设备后保留。不存商户信息、KEY、Cookie 或 CSRF；存储禁用时页面须明确提示。

### 3. 智能分析并确认分类

分析只读目录，不写商品/分类、不下载图片，可以离开页面。worker 通常在上一轮结束约 1 分钟后领取任务，刚排队的 0/0 不等于卡住。

智能分类模式的默认结构保留上游子分类，例如：

- AI工具 → Claude → 货源A → Claude Pro
- AI工具 → GPT → 货源A → AI Chat-GPT
- Facebook → 货源A → FB BM
- Telegram → 货源A → 上游原始子分类
- 其他 → 货源A → 未识别分类

智能分类建议器根据上游分类名分类，不根据商品名猜高置信目标。默认覆盖 GPT、Claude、Gemini、Twitter X、TikTok、WhatsApp、Telegram、Facebook、Instagram、LINE、Zalo、Kakao、Threads、LinkedIn、Reddit、Snapchat、Discord、Apple ID、Gmail、Outlook、短信接码、eSIM、TRON；邮箱保留 Gmail/Outlook 家族层。

智能分类模式应检查所有低置信及「其他」项目，必要时修改一级/二级目标；每个精确上游分类只分配一个目标。镜像模式不经过智能分类建议器，应核对冻结的完整路径和上游分类 ID，不能在确认时改名、换父级或改模式。多个待确认任务必须明确选择对应货源；轮询不应覆盖草稿。确认前核对数量、分类、加价。

单次上限 10000 商品、200 个商品分类；镜像另将必要祖先整树去重限为 2048。空目录、无效 UTF-8、控制字符及超过 128 字符的分类名仍拒绝，不静默丢弃；智能分类与确认列表原 200 门保持。

### 4. 后台入库与失败处理

| 状态 | 下一步 |
|---|---|
| 等待分析/入库 | 等 worker；长期无更新检查服务，不重复建任务 |
| 分析/入库中 | 看进度，必要时暂停/取消 |
| 待确认 | 检查方案及加价后确认 |
| 已暂停 | 继续当前工作或取消；暂停不会清零故障计数 |
| 入库中出现少量未导入项 | 后台仍处理正常商品，等待结果并查看异常清单 |
| 处理结束，有未导入项 | 正常商品已处理；核对并处理异常原因后，仅在按钮可用时点击「只重试未入库项」，不等于全部成功，也不要从头删除重建 |
| 连续/累计单件异常达到上限 | 该货源已停止；先核查上游整体状态，不继续请求几千件 |
| 旧网络传输/可重试 HTTP 详情失败且有「继续原任务」 | 原检查点入口保留，升级不自动继续；不保证上游恢复 |
| 旧码 `ITEM_DETAIL_FETCH_FAILED` 且有「继续原任务」 | 原因未分类；先检查再决定人工继续，不能当作已证实瞬时故障 |
| 详情兼容提示 | MIME 标签不标准但严格 JSON、协议和商品校验已通过，不是入库错误 |
| 新未知码 `ITEM_DETAIL_UNKNOWN_FAILED` | 先排查；不提供人工继续，不借用旧码兼容入口 |
| 已知业务/凭据/格式/预算失败 | 先处理明确原因，不自动重试或继续该失败任务 |
| 其他失败 | 按中文阶段/错误码处理原因，再分析 |
| 已取消 | 旧任务不可恢复；需要时重新分析 |
| 已完成 | 查看商品，配置后续同步 |
| 请求结果未知 | 先刷新核对，不重复提交保存/确认 |
| 页面进度读取暂时失败 | 保留最后已知进度；连续 3 次失败后停止自动轮询并提示刷新，后台任务状态另行核对 |

每轮最多 20 项，各商品独立提交；控制在当前单项安全边界生效，可能要等待上游请求结束，不强杀数据库交易。取消只停止剩余工作，不删除已完成商品/分类。可恢复失败的取消保留检查点和错误证据，之后不能继续该任务。

仅明确发生在写库前的远端单件错误可以隔离：传输/可重试 HTTP 在原有尝试耗尽后、明确未取得有效详情、纯商品字段格式/范围错误。缺失详情只表示未取得有效数据，不能据此判定下架或把库存清零。未知协议结构、凭据、来源/商品身份不一致、全局价格/币种、预算、本地缓存、分类事务、数据库及检查点错误仍停止。原全量扫描连续 5 件或当前未解决 100 件异常停止货源；成功或既有商品跳过会打断连续计数，跨后台批次不重置累计计数。

异常与进度原子保存，清单显示快照序号、固定原因与尝试次数，不输出商品名称或上游原文。未导入不能算成功或普通跳过。明确的详情 JSON 解码异常在写商品前隔离并继续，保持深度 32、16MiB、节点与安全上限；不是修补或接受坏数据。旧任务无明细时不补造，旧失败不会自动排队。新版 schema 4 可读旧记录，旧代码却不能读新字段／失败码；发生新处理后不得只切旧代码或恢复旧 jobs，须停止对账、保留最新状态并兼容前向修复。完整配对备份恢复仅限部署期且尚无新状态／业务写入。

「继续原任务」从原检查点继续尚未处理的商品；「只重试未入库项」只处理准确异常索引，保持原快照、分类、加价和货源身份，不重新扫描全目录或修改成功商品。补处理显示独立的本轮进度与结果；原 processed/total 不倒退、不重复累加，补入成功或确认已存在后从未导入数扣除并归入对应类别，失败保留准确索引和最新原因。后台不授予资格时不会显示按钮。重复点击或陈旧 revision 不能启动第二份工作，请先刷新核对，不反复提交。

补查轮只冻结当时最多 100 个失败索引，白名单商品级异常逐项记录后继续，不因前 5 项失败挡住尾项；时间、连接、请求次数及安全门不放宽。已提交游标以前的索引本轮不再处理，暂停／中断后保持游标和计数。旧规则停止的 5/14 显示「继续本次补处理」，沿原按钮只接续未补查 9 项；本轮处理完且后台资格成立时，按钮才显示「开始新一轮未入库项补查」。不自动开新轮，也不自动恢复未完成的原扫描。业务写成功但检查点未提交的崩溃窗口仍须按既有受管商品对账，不能承诺任意崩溃下网络 exactly-once。

详情诊断只展示本次已有响应的 data／首分类 children／首商品位置类型、实际数量和有界整数业务码，不保存正文或名称。空数组与空对象在关联解码后不可区分；未观察字段不补默认值，旧诊断不回填。摘要不改变业务判定，不能把 HTTP 200 或空详情解释为成功或已下架。

仅三个已支持精确只读详情接口把 MIME 当作兼容诊断信号；仍要求 HTTP 200、严格有界 JSON、协议业务成功与详情结构以及原商品、价格、币种和内容安全校验。不从 HTML 提取 JSON、不修补 JSON、不用目录数据补造详情，不新增“不安全兼容”开关。目录、图片、支付等规则不变，所有 URL/TLS、公网 DNS/IP 固定、禁代理/跳转和解析预算边界保留。

HTTPS 最多尝试 3 次（包含首次）；仅可重试网络错误和 HTTP `408/429/502/503/504` 使用 500／1000 毫秒基础退避。合法 `Retry-After` 只在剩余预算容得下等待和下一次尝试时采用，预算不足即停，不保证发满 3 次。连接 5 秒、请求 90 秒、单货源 120 秒、整轮 300 秒与 systemd 外层 8 分钟上限不变。凭据、策略、业务码、JSON、结构、商品字段、预算和数据库错误不自动重试。

传输失败、可重试 HTTP 失败及历史未分类 `ITEM_DETAIL_FETCH_FAILED` 的既有人工继续门不变。历史 `ITEM_DETAIL_RESPONSE_INVALID` 不全码放行：原可信 MIME 授权路径保留，另仅对 failed/import、无补处理轮且准确当前索引的 JSON 诊断（HTTP 200、cURL 0、json_valid=false、有效次数）开放原生继续，仍核对快照、加价、revision 与货源指纹。继续会重读当前未处理项一次，保留之前进度与异常索引，不重抓目录、不伪造旧原因。新未知失败不提供继续；全部失败任务不自动续跑。详细条件见[失败分类与恢复](../../../docs/TROUBLESHOOTING.md#详情读取失败怎样处理)。

任务卡的诊断、未导入项及任务详情三处展开／关闭状态按任务身份跨轮询保持；有效 summary／控制按钮焦点随重绘恢复。用户在请求等待时移出任务区则不抢焦点，目标消失或禁用也不改聚焦到别的按钮。读取失败保留旧进度与提示，下次成功清除提示；不承诺所有内容高度变化都不影响视口。

只有任务进度的只读轮询遇到明确 CSRF 校验失败时，才尝试受控续期：旧令牌签名仍须能按当前登录会话验证，最多续期和重读一次；换会话或无效签名拒绝，并非凡是校验失败都能恢复。会话变化或续期失败须刷新/重新登录。普通轮询暂时失败保留最后已知进度，连续 3 次失败停止自动轮询。保存、确认、暂停、继续、只重试未入库项、取消等写动作从不自动重放，页面读取失败不等于入库失败。

单件隔离的边界：价格/SKU 配置树或 INI 解析异常仍停止；未记录可信请求次数时显示「请求次数未记录」，不是零请求证明。最多 3 次只指每次客户端调用，不保证任意进程崩溃恢复后的累计次数。旧明细不可得的失败任务不可继续，但可明确取消。暂停/取消在当前商品检查点优先生效，暂停后恢复不能绕过已达到的异常上限。

### 5. 修改货源显示名

智能分类模式：在货源中心「编辑」，或原生分类页使用同页「修改货源显示名（同步所有分类）」入口。两处共用保存逻辑，支持任意合法昵称，不固定为货源A/B。镜像模式没有额外货源层；只在货源中心改后台显示名，不联动任何镜像分类。

上述分类联动只适用于智能分类模式：修改受管货源层名称及映射，分类 ID、父级和商品引用保持不变，不改平台、上游子分类、原生上游身份 shared.name。完全一致的同值保存无副作用；历史显示名和分类不同则须先修复一致性。

有活动任务或可恢复失败任务时，先完成或取消再改名。历史任务/快照不改写。原生受管名称不能单独编辑，旁边提供联动入口，普通分类不受影响。中断保留有界恢复记录，未核实前阻止继续入库，不通过另建分类掩盖问题。

### 6. 后续同步

入库正确后启用 PikaSupplySync basic 及其 timer，只更新已有 PKS1 受管商品；新品仍需按该来源已确定的模式重新分析、确认后入库。周期同步不新增、改名、移动、删除或重排分类，镜像模式也不例外。不同货源按 source_id 分离，不因子分类同名而混用绑定。

零库存也以 0 入库，主题会隐藏；之后成功同步正库存后恢复显示。管理员手动下架不被覆盖。本流程不包含付款、充值或订单测试。

### 7. 镜像升级与回退

已有分类映射的来源禁止在 `smart` 与 `mirror` 间切换；不能通过删除映射、改任务字段或只换旧代码绕过。部署期尚无新状态或业务写入时，才可使用已验证的完整配对恢复点：源码与 registry、站外配置、任务、快照、分类映射，以及数据库分类和商品引用必须对应同一恢复点。发生新写入后，先停止相关写入者、保留最新状态并对账，再决定兼容前向修复或另行批准的迁移；只恢复旧 jobs 或映射文件不能恢复整条分类链。

## 管理员参考

- 改名和 KEY/货币/汇率分开保存。协议、地址、商户 ID 是不可原地变更的绑定身份；高级删除/迁移须先备份并盘点引用，不删除有商品引用的货源。
- 旧字面规则和只读预览 API 仅保留后端兼容，普通页面不再显示；它不驱动智能分析、不能确认入库。诊断仅含固定阶段/类别、错误码、编号及有界 HTTP/cURL 数值、耗时、尝试数；不输出上游原异常、响应正文/头或秘密，不能据未分类错误猜测网络/TLS 根因。
- 最多 16 货源、64 任务、单快照 16 MiB；可继续的失败任务不会被轮转丢弃，必须先完成或明确取消。容量不足会提示，不扩大上限。终态轮转不能代替容量规划；部署前用 df/du 核对空间，另计备份余量，不自动清理业务数据或备份。
- 接入连接在 FPM 请求内，分析目录在 worker 内。本站 Nginx/FPM 接入请求链须匹配 150 秒；504 不证明服务器没有保存，先核对列表。
- 完整统一验收条件见根目录 docs/CATALOG_WORKFLOW_ACCEPTANCE.md；候选通过本地测试不等于完成目标站点或公开验收。

## 后台任务服务安装与移除

完成站点安装、扩展配置和手工 dry-run 验证后，可用同一个 root-only 安装命令同时管理 SupplySync 定时同步与 CatalogHub 后台任务。下面的路径、Web 用户和实例名必须替换为本站的真实值：

```bash
sudo /opt/pika-local-extensions/releases/CURRENT/scripts/scheduler.sh install \
  --site-root /opt/acg-faka \
  --web-user acgfaka-s0 \
  --instance s0 \
  --minutes 10 \
  --php /usr/bin/php
```

`--minutes` 只控制 SupplySync，允许 5–1440 分钟。CatalogHub worker 会在上一轮结束约 1 分钟后再次唤醒、每轮最多处理 20 项；上游较慢时两次启动的间隔会相应变长。没有待办任务时会立即退出，不会常驻。两个服务都以站点专用 Web 身份运行，且只允许写入站外 LocalExtensions runtime、公开图片缓存和经过 inode 绑定的 `runtime/config` 文件。

安装后检查四个 unit，并分别检查两个 service 的 systemd 安全边界：

```bash
sudo systemctl is-enabled pika-supply-sync-s0.timer pika-catalog-worker-s0.timer
sudo systemctl is-active pika-supply-sync-s0.timer pika-catalog-worker-s0.timer
sudo systemd-analyze verify \
  /etc/systemd/system/pika-supply-sync-s0.service \
  /etc/systemd/system/pika-supply-sync-s0.timer \
  /etc/systemd/system/pika-catalog-worker-s0.service \
  /etc/systemd/system/pika-catalog-worker-s0.timer
sudo systemd-analyze security pika-supply-sync-s0.service pika-catalog-worker-s0.service
```

移除时使用同一组站点身份参数；命令会同时移除两组 unit，不删除任务、快照、商品或分类数据：

```bash
sudo /opt/pika-local-extensions/releases/CURRENT/scripts/scheduler.sh remove \
  --site-root /opt/acg-faka \
  --web-user acgfaka-s0 \
  --instance s0 \
  --php /usr/bin/php
```

移除命令不会强杀正在执行的 oneshot。若任一服务仍在运行，它会停止并保留现状；应等待当前单项安全边界结束后重试。安装或移除中途失败时，脚本会事务式恢复原有四个 unit 和两个 timer 的启用/运行状态；若报告回滚不完整，必须保留它输出的 recovery 目录并停止人工覆盖。
